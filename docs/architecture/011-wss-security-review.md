# Independent security review: Plan 011 WSS

**Date:** 2026-11-04

**Verdict:** WSS end-to-end encryption is not approved for implementation.
**Scope:** This review covers [the ADR](011-client-ecs-adr.md), [the WSS draft](011-wss-protocol.md), [Plan 011](../../plans/011-client-ecs-resilience.md), and the current account, key, and remote-peer code. It is an independent review. It does not approve its author’s draft.

The role split, local Provider and Host lifecycle work, and a Bun HTTP or SQLite service skeleton can continue. These tasks must not add WSS keys, handshakes, encrypted frames, or production credentials. The isolated library experiment is authorized with generated test identities, no product traffic, no production keys, and no root manifest change. Its result needs review before a separate, controlled development adapter can proceed. That adapter does not need a complete product or three-platform hardware proof. It must use local test traffic and no production keys. Physical device proof on all three target platforms is required before release. None of these steps approves production WSS today.

## Findings

| ID | Severity | Finding | Required closure |
|---|---|---|---|
| WSS-1 | Blocker | No reviewed Noise library or pattern is selected. The lockfile has `@noble/curves` and `@noble/hashes`, which provide primitives, not a Noise handshake. The vendored Baileys `noise-handler` is application-specific code and uses Node crypto. | The authorized isolated experiment checks an exact library release in Node/Bun and a standard browser harness with generated identities. It does not change the root manifest or use product traffic or production keys. Review that evidence before separately approving a small local development adapter. The adapter does not wait for a complete product or three-platform hardware proof. Before release, prove the exact selected package and adapter on physical Electron macOS ARM64, Electron Windows ARM64, and the actual Android target. Do not build a handshake from primitives. |
| WSS-2 | Blocker | First-pair identity and device authorization are not independent of the ECS control plane. A ticket is an account claim; it does not prove that a Host owner approved a device. The current peer code creates a new Ed25519 client key per connection, while the current host identity is a stable Ed25519 key. Noise 25519 uses X25519 DH keys. | Create persistent peer identities. Pair through a Host-local owner action and compare an out-of-band authentication string for the Host and device identities. Store the device identity and its capability ceiling in a Host-local grant. A ticket or gateway response must never create or expand this grant. Bind each Noise X25519 static key to its stable Ed25519 peer identity using the selected library’s signed binding. Use the existing host key only if its encoding and identity mapping are verified; otherwise pair a new persistent identity. Never derive an X25519 secret from an Ed25519 seed. |
| WSS-3 | Blocker | Account and relay trust are on one ECS. Process separation does not isolate secrets from an ECS root compromise. The draft says the account signer is isolated from the relay, but no deployment evidence confirms that boundary. | State whether the full ECS and account signer are trusted. If they are, limit the claim to protection from a compromised relay process and require Host-local grants to cap permissions. If the design must resist ECS-root compromise, keep the account signing root outside that host and pin its public root at the endpoints. Keep account JWT keys, Host identity keys, device identity keys, and Noise DH keys separate. A key change needs an old-key-signed handover or a new owner-confirmed local pairing; an account or gateway update alone is not enough. |
| WSS-4 | Blocker | The encrypted frame, replay state, and restart epoch are not defined tightly enough to reject frames routed to the wrong peer or replayed across connections. | Authenticate the protocol version, session ID, Host ID, user ID, Host peer ID, device peer ID, grant ID, `authEpoch`, `grantEpoch`, `hostEpoch`, `deviceEpoch`, connection generation, channel, sequence, and request or operation ID inside the Noise-protected payload. Treat every outer relay route, `from`/`to`, and relay ACK as untrusted. Use a fresh Noise handshake and fresh keys on every reconnect. Let the library own nonce state; reject duplicate or out-of-order sequence values within a session. Persist separate monotonic `hostEpoch` and `deviceEpoch` values in the durable local state of each endpoint; increment each before that endpoint accepts connections after process start. Each device terminal operation records its current `deviceEpoch`. Use a new random connection generation per completed handshake. If local state rolls back or is lost, stop remote service on that endpoint until its identity is re-paired. Do not resume an old cipher key or counter after restart. |
| WSS-5 | Blocker | The draft has account `authEpoch` but no defined per-device grant epoch, bounded authorization freshness, or cursor scope. A live session can outlast a missed revoke event. | Keep three scopes distinct: account `authEpoch` for account or membership changes; monotonic `grantEpoch` for one Host/device grant; and local `hostEpoch` for Host process restarts. Require a signed authorization lease bound to the Host, user, membership, device peer ID, grant ID, capability set, and both authorization epochs. Use the existing 180-second ticket lifetime as the maximum lease age and refresh at least once per 60 seconds. If refresh has a temporary network or service failure, keep using the still-valid signed lease within its exact scope and retry in the background with backoff. A verified newer epoch revokes the affected access at once. At lease expiry, with no fresh valid lease, close the session and fail closed for files, terminal, API, chat, and event operations. A failed or invalid refresh cannot extend or widen the old lease. The durable revoke outbox is a fast path, not proof of freshness. Enforce the intersection of account membership, the Host-local grant, the capability registry, and OS permissions. Partition cursors by `(host, user, device, grant, capability, hostEpoch)`. Filter events before assigning or advancing a cursor. A grant change invalidates old cursors and requires a new authorized snapshot. |
| WSS-6 | Blocker | Transport ACK, Host receipt, and execution on the receiving device can be confused during a disconnect. The proposed sidecar cannot commit atomically with `openbot.db`; terminal process effects cannot be rolled back. The memory caps also lack an aggregate enforcement rule. | Name transport ACK as receipt by the relay only. For chat written by the Agent Host, send a Host receipt only after the authoritative SQLite write and idempotency key commit in the same `openbot.db` transaction. Keep a sidecar as a rebuildable hint; do not ACK durable acceptance from it. This Host receipt does not confirm terminal execution. The receiving device owns the terminal ledger and output ring. Before spawn, it must persist `operationId`, exact request hash, state, and `deviceEpoch` in its own durable store. A duplicate ID with the same request returns device-saved state; a different request fails. After a crash or uncertain process identity, the device reports `unknown` and never runs the command again automatically. It may reattach only after it validates the recorded terminal session, device epoch, PID, and OS process start time. The Host only authorizes and relays; it cannot claim an execution result. Keep the 1 MiB output ring per session on the device, cap active terminal sessions at four per device and four aggregate at a Host, and enforce the separate WSS per-connection and global relay caps with backpressure. Do not spool terminal output to gateway disk. Define an output-gap response. At the 30-minute detach limit, the device closes the process and records its final or unknown state; reconnect must never rerun it. |

## Library evidence

The local package inventory contains no Noise implementation. The WhatsApp vendor’s [`noise-handler.ts`](../../packages/whatsapp/vendor/baileys/src/Utils/noise-handler.ts) implements a WhatsApp-specific handshake and transport. It is not a general Noise library for this WSS protocol.

One candidate for the isolated spike is [`@chainsafe/libp2p-noise@17.0.0`](https://www.npmjs.com/package/@chainsafe/libp2p-noise/v/17.0.0). I inspected the published package archive and metadata without installing it. It uses `Noise_XX_25519_ChaChaPoly_SHA256`, signs its X25519 static key with a libp2p identity key, checks an expected remote identity, and has a browser build that uses pure JavaScript noble crypto. Its license is Apache-2.0 or MIT. Its API is a libp2p connection encrypter, not a WebSocket API. The package advertises browser tests, but I found no Android WebView or React Native support claim. This is a candidate, not a library approval. The WSS draft must change from candidate XK to the exact library-supported XX pattern if this package passes the spike. If the project keeps XK, it must select and review a library that supports XK on all target runtimes.

The current remote ticket code sets a 180-second lifetime in [`remote-control-plane.ts`](../../apps/auth-api/src/server/remote-control-plane.ts#L67) and places `hostId`, `userId`, `membershipId`, `role`, `authEpoch`, and the client-supplied public key in the signed ticket ([ticket issuance](../../apps/auth-api/src/server/remote-control-plane.ts#L1918)). It has no WSS device grant. The current client creates a new Ed25519 identity for each peer connection ([`remote-peer.ts`](../../packages/team-client/src/remote-peer.ts#L908)). The host key handover code already requires both old and new Ed25519 keys to sign a rotation ([`remote-control-plane.ts`](../../apps/auth-api/src/server/remote-control-plane.ts#L755)); this is a useful precedent, but it does not bind a Noise DH key by itself.

## Gate result

The WSS handshake, key management, encrypted frame, relay authorization, and remote file or terminal operation paths remain blocked. Close WSS-1 through WSS-6 in the protocol and return for independent review. The isolated library experiment is authorized. Review its evidence before any controlled development adapter. Physical proof on Electron macOS ARM64, Electron Windows ARM64, and the actual Android target is a release gate; it is not a prerequisite for that limited adapter.

This review did not run tests or builds and did not access ECS, Google, DNS, production credentials, or deployment systems. Library research used only public npm metadata and the published package archive. The ECS process and key isolation claim remains unconfirmed because no ECS environment was inspected.
